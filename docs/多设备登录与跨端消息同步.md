# 多设备登录与跨端消息同步：一次网关改造记录

## 一、问题从哪来的

我们有个自研的 IM 网关，前端用 WebSocket 长连接，后端用 HTTP 调各业务服务。一开始设计得很简单：一个用户在一个时间点只允许一条 WebSocket 连接，网关里用「用户 ID → 连接」的映射，发推送时查到这个连接，发就完事。

上线没多久就出问题了：用户 A 在手机上登录着，再在电脑上登录，电脑能连上，但手机被顶掉线；反过来也一样。客服收到的反馈基本都是「换设备就收不到消息」「两个设备不能同时在线」。根因就是网关侧只认「一个 uid 对应一条连接」，后登录的把先登录的覆盖了，而且断线时也按 uid 删，导致同账号其它设备的连接状态被一起清掉。

所以需求很明确：**同一账号支持多设备同时在线，并且每条消息要能同步到该账号当前在线的所有设备**。也就是说，推送不能只发「一个连接」，而要发「该 uid 下的所有连接」。

我们当时也考虑过「一个 uid 对应一个 conn，但 conn 背后维护多条物理连接」之类的方案，但那样要在网关内部再做一层会话与连接的绑定，复杂度反而更高。最终选的是最直接的一种：**用 session_id 做连接的唯一键，用 uid 做「推给谁」的聚合键**，发消息时按 uid 查出所有 session，再按 session 查出所有 conn 逐个发。这样既清晰，也方便后面做「按设备踢线」「按会话过期」等扩展。

## 二、先想清楚「连接」和「会话」

多设备的前提是：每次登录产生一个**登录会话**，一个会话对应一条 WebSocket 连接。同一个用户可以有多个会话（手机一个、PC 一个、Pad 一个），每个会话有唯一 ID，我们叫 `session_id`，由登录接口生成并下发给客户端，建连后首包会带上这个 `session_id` 做鉴权。

之前网关里的结构本质是：

- `uid -> conn`（一个用户只存一条连接）

要支持多设备，就必须改成：

- 一个用户对应**多条**连接；
- 每条连接唯一由一个 `session_id` 标识；
- 发消息时，通过 uid 找到该用户**所有**的 session，再通过每个 session 找到对应的连接，逐条发送。

所以核心就是两套映射：

1. **session_id → connection**  
   用来精确定位「这条连接」：断线、超时、踢人时，只删这一个 session，不影响同用户其它设备。

2. **uid → 多个 session_id**  
   用来做「按用户推消息」：给某用户发通知时，查到他名下所有 session_id，再逐个查到 conn 去发。

这样既满足「多端同时在线」，又满足「按会话维度的生命周期管理」，不会误伤同账号其它设备。

## 三、会话和连接在网关里怎么存

我们网关是用 C++ 写的，连接管理放在一个叫 `Connection` 的类里，内部原来大致是：

- `_uid_connections`：`map<uid, conn>`，一个用户一条连接；
- `_conn_clients`：`map<conn, (uid, ssid)>`，反向查这条连接是谁、哪个会话。

改造后的目标结构是：

- **session_id → connection**  
  用 `_ssid_connections`：`map<session_id, conn>`。  
  建连并鉴权成功后，用当前会话的 `session_id` 做 key 存进去；断线或登出时，用当前 conn 反查出 `session_id`，只删这一条。

- **uid → 多个 session_id**  
  用 `_uid_sessions`：`map<uid, set<session_id>>`。  
  同一个 uid 可以对应多个 session_id（多设备），插入 / 删除时只增删当前会话对应的那个 session_id，不动别的。

- **connection → (uid, session_id)**  
  保留 `_conn_clients`：`map<conn, {uid, ssid}>`。  
  用途不变：断线时根据 conn 查出 uid 和 ssid，去 `_uid_sessions[uid]` 里删掉这个 ssid，再删 `_ssid_connections[ssid]` 和 `_conn_clients[conn]`。

这样，**建立连接**时：在 `_uid_sessions[uid]` 里 insert 当前 `session_id`，在 `_ssid_connections` 里写入 `session_id -> conn`，在 `_conn_clients` 里写入 `conn -> (uid, ssid)`。  
**断开连接**时：用 conn 从 `_conn_clients` 取出 uid、ssid，从 `_uid_sessions[uid]` 里 erase 这个 ssid（若 set 空了就删掉 uid 这一项），再删 `_ssid_connections[ssid]` 和 `_conn_clients[conn]`。  
**按用户发消息**时：从 `_uid_sessions[uid]` 取出所有 session_id，对每个 session_id 在 `_ssid_connections` 里取 conn，组成列表返回，调用方遍历这个列表逐个 send。

实现时注意并发：这些 map 都在网关进程内，用一把 mutex 包住即可，避免同一时刻有人插连接、有人删连接、有人在遍历发消息导致竞态。

接口层面，原来对外暴露的是 `connection(uid)` 返回一条 conn，现在改成 `connections(uid)` 返回 `vector<conn>`。所有「按 uid 取连接再发消息」的代码，从「取一条、判空、发」改成「取列表、遍历、每条都发」。payload 可以只序列化一次，在循环里复用，减少重复计算。

## 四、登录与登出：和「设备」的关系

多设备要做得干净，登录 / 登出必须和「设备」绑定，而不是和「用户」绑定。我们当时的做法是：

- 登录请求里带 `device_type`（例如 pc / ios / android / web），服务端生成唯一的 `session_id`，把 `(session_id, uid, device_type)` 写入 Redis（会话表），同时用 `uid|device_type` 作为「该设备是否已登录」的标记 key，也写 Redis。
- 同一 `uid` 下，不同 `device_type` 可以各有一个在线会话；同一 `device_type` 重复登录时，可以按业务选择「踢掉旧会话」或「拒绝新登录」，我们选的是同一设备只允许一个会话，新登录顶掉旧的。
- WebSocket 断线（onClose）时，用当前 conn 查出 uid 和 session_id，再用 session_id 从 Redis 查出 device_type（或建连时在内存里也存一份），只删 Redis 里 `uid|device_type` 的在线标记，并删内存里该 session_id 对应的连接；**不要**按 uid 整户踢线。

这样，多设备登录、单设备单会话、断线只影响当前设备，逻辑就一致了。

## 五、推送：从「发一条」改成「发该用户所有连接」

以前网关里所有「给用户 A 发一条 WebSocket 消息」的地方，都是类似：

```text
conn = get_connection(uid)
if conn then conn.send(payload)
```

现在要改成「给用户 A 的所有在线设备发」：

```text
conns = get_connections(uid)   // 返回 list<conn>
for conn in conns do conn.send(payload)
```

也就是说，原来 `Connection` 提供的接口是「按 uid 取一条 connection」，要改成「按 uid 取到该用户所有 connection」。我们内部实现就是：先查 `_uid_sessions[uid]` 得到所有 session_id，再对每个 session_id 在 `_ssid_connections` 里取 conn，组成列表返回；发送方遍历这个列表逐个 send。

需要排查所有「按 uid 查连接再发消息」的调用点，统一改成「按 uid 取连接列表，再循环发送」。我们这边涉及的大类包括：好友申请/处理/删除通知、会话创建通知、单聊与群聊新消息通知、频道消息通知等。只要之前是用「一个 uid 对应一个 conn」发的，都要改成「一个 uid 对应多 conn，全部发一遍」。这样多端消息就自然同步了。

改造时建议全局搜 `get_connection(uid)` 或你们项目里等价「按 uid 取单连接」的接口，逐个看调用处：若是「取到连接后发一条 WebSocket 消息」，就改成「取 connections(uid)，对每个 conn 发同一条消息」。发好友申请通知、好友处理结果、会话创建、新消息推送、频道消息推送等，逻辑都一样：**通知对象是一个 uid，但要发到该 uid 当前所有在线设备**，所以必须遍历该 uid 下的所有连接。改完编译跑一遍，确认没有漏掉的单连接发送点即可。

## 六、一些实现上的坑

**1. 连接指针的生命周期**  
WebSocket 断线时，框架会回调 onClose，此时 conn 可能正在被别处引用（例如正在遍历发消息）。我们是在 onClose 里先把该 conn 从上述三个 map 里删掉，再做业务逻辑（如清 Redis），这样后续再按 uid 查就不会再拿到这条已断开的 conn；若某次 send 时 conn 已失效，由框架或上层做错误处理即可。

**2. 同一设备多端（例如浏览器多 tab）**  
若业务允许同一 device_type 下多会话（如多 tab 各建一条连接），则 `uid|device_type` 一个 key 就不够用了，可以改成「每个 session_id 一个在线标记」，或「uid|device_type」下存一个 session_id 列表，按业务决定踢人策略。我们当前是「同一 device_type 只保留一个会话」，所以逻辑简单。

**3. 顺序与去重**  
多端同时在线时，同一条业务消息会发多份（每个设备一份），这是预期行为；若业务有「已读」「未读」等状态，需要按设备或按会话维护，和「推了几条连接」是两回事。消息顺序我们没做额外保证，就是按「当前查到的连接列表」顺序发，一般够用。

**4. 兼容老逻辑**  
若有历史代码是「我只要该用户任意一个连接」的（例如只做单端推送的灰度），可以在 Connection 里再封装一个 `get_any_connection(uid)`，返回 `get_connections(uid)` 的第一个或随机一个，便于兼容。

**5. 空列表不是错误**  
用户可能当前没有任何在线连接（全退了或还没建连），这时 `connections(uid)` 返回空列表是正常情况，发送方直接跳过即可，不要当成异常打满日志。只有「业务上期望他在线却拿不到任何连接」时才需要告警或降级处理。

## 七、小结

多设备登录 + 跨端消息同步，本质是两件事：  
一是**会话与连接一一对应**，用 session_id 做连接的唯一键，断线、踢人只动当前会话；  
二是**按用户推消息时发所有连接**，用 uid → 多 session_id → 多 conn 的映射，把「发一条」改成「发该用户当前所有连接」。

网关侧把「uid → 单 conn」改成「uid → 多 session_id → 多 conn」之后，再配合登录层「同一 uid 不同 device_type 可多会话」的策略，就能在不改业务协议的前提下，支持多设备同时在线和消息多端同步。我们按这个思路改完，多端同时收消息、换设备不再互相顶线的问题就都解决了。

整体改动量不大：连接管理类里多两张表（session→conn、uid→sessions），改掉 insert/remove 的维护逻辑，对外接口从「取一条」改成「取列表」；然后所有按 uid 发推送的地方统一改成遍历列表发送。登录与 Redis 侧只要保证「一个会话一个 session_id、按设备维度做在线标记」，和网关的「按 session 管理连接、按 uid 聚合多连接」就能对上。如果你也在做类似改造，希望这篇能少踩点坑。
